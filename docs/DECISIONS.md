# Notification Service Architectural Decisions & Open Questions

This document records architectural decisions, pending team alignments, and working assumptions for the Notification Service in the Fashion Wholesale Distribution ERP.

---

## Open Questions

| Item / Topic | Current Assumption & Proposed Choice | Alternative Options Considered | Context & Architectural Impact | Status |
|---|---|---|---|---|
| **Final role names** | Assumed roles are `admin`, `manager`, `purchasing`, `warehouse`, `sales`, and `finance`. Role checks will use configurable string mappings. | Granular permission scopes (e.g. `notifications:write`, `email:manage`) vs. hierarchical RBAC. | Dictates role-based access checks for `/admin/*` routes and role-targeted notification routing. | Open |
| **JWT claim names** | Standard claims: `sub` (User UUID), `roles` (string array), `email` (string), and `exp` (UNIX timestamp). | Custom claims like `user_id`, or namespaced URI claims (e.g. `https://erp.internal/claims/roles`). | Auth token parser expects these specific keys to authenticate and extract recipient context. | Open |
| **Kafka topic names, partition counts and retention** | Domain-oriented topics: e.g. `erp.auth.events`, `erp.purchasing.events`, `erp.inventory.events`, `erp.sales.events`, `erp.returns.events`, `erp.finance.events`, `erp.platform.events`. Defaults: 6 partitions, 7 days retention. | Single unified topic `erp.events.all` vs. per-event-type topics (`erp.events.order_confirmed`). | Determines consumer group concurrency, partition scaling, and storage footprints. | Open |
| **Who creates topics in shared environments** | Infrastructure/DevOps provisioning (Terraform, Strimzi, or Docker Compose init scripts) creates topics ahead of time. Service only relies on auto-creation during local development. | Services automatically creating topics via Kafka AdminClient on startup in staging/production. | Automatic creation in production risks incorrect partition counts or improper replica factors. | Open |
| **Kafka security (PLAINTEXT locally, SASL_SSL elsewhere)** | Configurable security protocol: `PLAINTEXT` for local development Docker Compose; `SASL_SSL` (SCRAM-SHA-512) for staging, production, or managed Kafka clusters. | Hardcoded plaintext vs. mTLS across all environments. | Requires configuration fields for client certificates, username, password, and security protocol in environment variables. | Open |
| **Whether a schema registry is used** | **Assumption**: No Confluent/Apicurio Schema Registry is used. Strict JSON envelope format specified in `CONTEXT.md` Rule 6 serves as the contract. | Confluent Schema Registry with Avro, Protobuf, or JSON Schema. | Eliminates extra infrastructure dependency for a 3-member college project while preserving schema clarity through additive versioning. | Open |
| **How recipient email and roles are obtained** | **Assumption**: Auth service domain events (`user.created`, `user.updated`, `user.roles_changed`, `user.deactivated`) populate a local read-only projection table (`user_identities_projection`) in `notification_db`. | 1. Synchronous REST call to Auth Service on every notification (violates decoupling and transaction rules).<br>2. Expecting recipient email directly inside every domain event payload. | Maintains strict microservice isolation and local database independence without cross-service database access or blocking remote calls. | Open |
| **Who owns `GET /operations`** | Saga Orchestrator / Core API Gateway owns persistent tracking and the `GET /operations` endpoint; Notification Service only emits SSE live status events (`event: operation`). | Notification Service maintains and serves the entire operational audit log via `GET /operations`. | Clarifies scope boundary between operation workflow orchestration and user push notification streaming. | Open |
| **Email provider (SMTP/SES/SendGrid)** | Pluggable email driver interface: default to SMTP with Mailpit/Mailhog for local Docker Compose dev, and AWS SES or SendGrid for staging/production via environment configuration. | Fixed single provider (e.g., hardcoded SMTP or SendGrid API only). | Allows local development without external credentials while supporting high-throughput cloud delivery in production. | Open |
| **Where attachment files live** | **Decision**: Attachments not supported yet; file storage is an open team decision. Requests providing `attachments` return HTTP 400 `validation_failed` (`attachments_not_supported`). | 1. Local filesystem shared volume.<br>2. PostgreSQL `bytea` blob columns.<br>3. Entire attachment payloads passed in memory. | Avoids bloat in Postgres `notification_db`, prevents large memory consumption in message brokers, and guarantees secure access. | Decided (attachments not supported yet) |
| **Migration tool** | Migrations written as plain SQL files (`000001_name.up.sql` / `.down.sql`) in `migrations/`. Local development and Makefile convenience target will use `golang-migrate`, with no migration library hardcoded in the Go binary runtime. | 1. `pressly/goose`<br>2. `dbmate`<br>3. In-app migration runner embedding SQL files. | Ensures independence from specific Go ORMs/frameworks until the 3-member team makes a final project-wide selection. | Open |
| **Whether producers already publish through an Outbox** | **Assumption**: Producer services implement the Transactional Outbox pattern so messages published to Kafka are guaranteed to have committed transactions and no phantom events are emitted. | Non-transactional publishing directly inside application controllers (risks dual-write inconsistencies). | Upstream producers must adopt Outbox pattern to ensure message reliability and prevent missing notifications. | Open |
